## 社区如何使用 Tunix 和 TPU 训练 Gemma「学会思考」【⭐⭐】

**来源：** Google AI
**链接：** https://developers.googleblog.com/how-the-community-trained-gemma-to-think-with-tunix-and-tpus/
**关键词：** Gemma 推理训练、Tunix Hackathon、GRPO、SFT、社区后训练、结构化推理

### 摘要

Google 在 Kaggle 上举办了 Tunix Hackathon，目标是让社区开发者用极小的计算预算（单台 Kaggle TPU v5e-8，限时 9 小时）把非推理版小模型（Gemma-2-2B 和 Gemma-3-1B）训练成具备结构化推理能力的模型。超过 11,000 人报名，300+ 份高质量提交，证明社区完全可以玩转推理训练。

**获奖方案核心思路都是「SFT 打底 + 强化学习拔高」**的多阶段管线：

🥇 **第一名 G-RaR**：先用 SFT+LoRA 在 ~33k 样本上训出 `<reasoning>...</reasoning>` 格式基线，再用 GRPO 做对齐，关键创新是用一个较大的 judge 模型（Gemma-3-12B）按任务特定评分标准（Rubric）评估推理质量，把离散评分转为连续奖励信号。为了在 TPU v5e-8 上同时跑策略模型和评判模型，团队用了 split-mesh 架构分开放两个模型。

🥈 **第二名 Pinocchio-1B**：三段式管线——SFT 蒸馏（70k 提示，OSS-120B 作 teacher + Gemini 做任务路由）→ SimPO（替代内存重的 DPO 来强制 XML 格式规范，防止模型靠输出更长来作弊）→ GRPO（用 Gemini 2.0 Flash 异步评分，奖励准确性、逻辑和格式）。团队还自己扩展了 Tunix 库，注入了自定义 SimPO 损失函数和高吞吐异步评估引擎。

🥉 **第三名 IDEA-E**：把 IDEA-E 伦理推理框架蒸馏进 2B 模型，用课程引导的 GRPO + TF-IDF 奖励替代慢 LLM judge，通过奖励使用上下文相关词汇来防止模型「说车轱辘话」。

**值得关注的荣誉提名**包括：on-policy distillation（不用静态数据集，teacher 根据 student 的实时输出动态生成推理轨迹）、自建 Deep-CoRGI 数据集 + 自训 ThoughtTeacher 奖励模型。此外还有医疗、化学、法律、机器人等垂直领域的推理训练方案。

核心结论：**小型模型的推理能力不再是巨头专利**，Tunix + 免费 Kaggle TPU 让社区开发者也能产出可用产品。所有方案已开源在 GitHub 上。

结合同日发布的 Opus 4.8 和 Claude Code 动态工作流来看，Anthropic 的策略很清晰：**一手拿钱堆算力，一手出货抢市场**。9650 亿估值意味着投资人对 Claude 成为下一代企业计算入口的判断。

## Claude Code 引入动态工作流（Dynamic Workflows）【⭐⭐⭐】

**来源：** Claude Blog
**链接：** https://claude.com/blog/introducing-dynamic-workflows-in-claude-code
**关键词：** Claude Code、动态工作流、并行 Subagent、端到端自动化、Ultracode

### 摘要

Claude Code 推出动态工作流（Dynamic Workflows），让 Claude 能够自动编排并行 Subagent 来处理大规模端到端任务。原本需要按季度规划的工程工作，现在可以在几天内完成。

**核心能力：** Claude 动态生成编排脚本，在单次会话中并行运行数十到数百个子 Agent，每个子 Agent 独立执行子任务，且在结果交付前自动验证——相当于 Claude 自己当项目经理，拆任务、派活、检查，最后汇总给你。

**典型场景：**
- **全代码库 Bug 排查/安全审计：** 并行搜索整个服务或仓库，对每个发现独立验证，确保报告只包含真正的问题
- **大规模迁移/现代化：** 框架替换、API 弃用迁移、跨数千文件的语言移植，端到端搞定
- **关键任务双重检查：** 高风险任务中 Claude 会启动多个独立尝试和对抗性 Agent 来验证结果

**使用方式：** 已上线 Claude Code CLI、Desktop 和 VS Code 扩展（Max/Team/Enterprise 计划），支持 API、Amazon Bedrock、Vertex AI 和 Microsoft Foundry。两种启动方式：直接让 Claude 创建 Workflow，或开启 `ultracode` 设置（通过 effort 菜单，将 effort 设为 xhigh 后 Claude 自动决定何时使用 Workflow）。

**注意：** 动态工作流可能消耗大量 token，建议先从范围明确的小任务开始熟悉。

**评价：** 这是 Claude Code 从「智能助手」到「工程自动化平台」的关键一步。动态工作流本质上是把 Map-Reduce 思想用在 Agent 编排上——拆解→并行执行→交叉验证→汇总。结合同日发布的 Opus 4.8（长时任务一致性提升）和 650 亿融资，Anthropic 的产品路线非常清晰：全力抢占企业级 AI 工程自动化市场。

## Surge AI：在 MCP Agent RL 环境上后训练 Qwen3.5，跨 Benchmark 泛化验证【⭐⭐】

**来源：** Surge AI
**链接：** https://www.surgehq.ai/blog/cross-benchmark-generalization-for-long-horizon-agentic-tasks
**关键词：** Agent RL 后训练、Qwen3.5、跨 Benchmark 泛化、SFT+RL 管线、GSPO、Toolathlon、MCP

### 摘要

Surge AI 发布了一篇技术博客，报告他们在自家 Agent RL 环境上对 Qwen3.5-122B-A10B（MoE）做后训练的结果，核心验证了一个关键问题：**在特定 RL 环境上训出来的 Agent 能力，到底能不能迁移到训练集之外的真实 Benchmark？**

**训练环境：** Surge 的 RL 环境覆盖 27 个任务类别，每个任务通过 MCP Server 暴露工具（包括 Playwright 浏览器、Excel 读写器、文件系统、日历 API 等），由确定性 Python grader 打分。任务是典型的长时域（long-horizon）场景——需要 25-40+ 轮工具调用、80K-100K token，不是简单的单次 function calling。

**训练管线：** 两阶段——SFT 打底 + RL 拔高。直接用 RL 训练行不通（基线模型 pass@4 只有 16.8% 的任务能产生任何 reward），所以先用 SFT 扩大可解任务面，再用 GSPO 做优势估计。还有一个关键设计：把 grader 的逐条评分转成 dense reward（完成度百分比），而不是简单的 binary pass/fail。换成 dense reward 后，平均每任务 reward 从 0.30 升到 0.51，产生有效信号的任务比例从 16.8% 跳到 82.7%。

**核心结果（pass@1）：**
- 训练 distribution holdout：+17.3pp
- **Toolathlon：+9.6pp**（从 23.5% → 33.1%，与 GPT-5.5 medium 仅差 ~1pp）
- **τ²-Bench：+5.3pp**（同样逼近 GPT-5.5 medium）
- **BFCL-V4：+3.5pp**

在三组外部 Benchmark 上均观察到正向迁移——这意味着训练出来的不是「背题库」式的环境特化，而是真正的工具使用和长程规划能力的提升。

**训练后自发出现的行为变化（未经 reward 显式奖励）：**
1. **并行工具调用：** 模型开始在一次 turn 中同时发出多个独立调用（如同时读多个 memory key），减少了 context window 耗尽导致的失败。基线和 SFT-only 检查点没有这个行为。
2. **任务闭环（task closure）：** 基线模型常出现「收集了证据但不产出最终 artifact」的问题（比如 Office 任务里读了文件、解析了表格、写了中间脚本，但最后不写入输出文件），训练后模型能端到端完成任务并验证输出。

**评价：** 这篇文章的核心价值不在模型能力绝对值有多高（33% 的 Toolathlon 离实用还远），而在于**方法论上的严谨——用外部 Benchmark 而非训练集 holdout 来衡量泛化**。Surge 团队刻意没有用这三个外部 Benchmark 做任何超参调优、checkpoint 选择或 reward 设计，这种做法在行业里不算默认操作（很多论文只报 holdout）。结果也验证了一个重要模式：SFT 解决 reward 稀疏、dense reward 驱动有效 RL、能力可以跨分布泛化。

## OpenJarvis v1.0 发布：Stanford 出品，本地优先的个人 AI Agent 框架，原生支持 Ollama【⭐⭐】

**来源：** Ollama
**链接：** https://ollama.com/blog/openjarvis
**关键词：** OpenJarvis、本地 Agent、Ollama、Stanford Hazy Research、Intelligence Per Watt、个人 AI

### 摘要

Ollama 宣布 OpenJarvis v1.0 正式发布——这是 Stanford 的 Hazy Research 和 Scaling Intelligence 实验室联合打造的开源个人 AI Agent 框架，核心理念是「Intelligence Per Watt」，即本地优先运行，云端按需可选。

**核心定位：** 本地模型已经能胜任绝大多数日常对话和推理任务，但大多数个人 AI 产品仍然把所有请求发往云端。OpenJarvis 把本地运行设为默认——模型本地推理，云端可选用，同时追踪能耗、成本和延迟。

**安装与集成：** 安装脚本自动检测已有 Ollama 安装。通过 `jarvis model pull` 拉取任意 Ollama 模型，配置文件设定默认模型和推理引擎。

**三大内置 Agent 预设：**
1. **Morning Briefing（晨间简报）：** 接入日历、邮箱和当日新闻，生成个性化每日摘要
2. **Deep Research（深度研究）：** 跨网页和本地文档搜索研究，返回带引用的答案
3. **Local Coding Agent（本地编码）：** 在本地执行代码的编程助手

**完整产品 vs 底层框架：** 相比 LangChain / CrewAI 这类需要自己搭管线的框架，OpenJarvis 更像一个开箱即用的本地 Agent 产品——有 preset、有 config、有工具链。类比来说有点像本地版的 ChatGPT Operator，但完全运行在你自己的硬件上。

**评价：** 这个项目的意义不在于技术有多深，而在于它代表了一个重要趋势——**从「云端 AI 服务」到「本地 AI 操作系统」的范式转移**。当 Anthropic 和 OpenAI 在云端卷 Agent 能力时，学术界和开源社区在探索如何让 Agent 跑在你自己的设备上。Ollama 作为本地推理的事实标准，与 OpenJarvis 的组合可能会催生一波本地 Agent 应用。不过 v1.0 仍然是早期阶段，离普通用户能无障碍使用还有距离。
