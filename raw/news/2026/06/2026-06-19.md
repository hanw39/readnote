## Steering Claude Code: CLAUDE.md files, skills, hooks, rules, subagents and more【⭐⭐】

**来源：** Claude Blog
**链接：** https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more
**关键词：** Claude Code、指令系统、Skills、Hooks、Subagents、Rules、Output Styles、CLAUDE.md

### 摘要

Anthropic 发布了一篇系统性的技术博文，全面梳理了 Claude Code 中控制 AI 行为的七种方法，并给出了每种方法的加载时机、压缩行为（compaction）、上下文成本和适用场景的决策框架。

**七种方法的对比：**

| 方法 | 加载时机 | 压缩行为 | 上下文成本 | 适用场景 |
|------|----------|----------|------------|----------|
| **CLAUDE.md（根目录）** | 会话开始时加载，全程驻留 | 压缩后重新读取，有记忆化缓存 | 高（每行都消耗token） | 构建命令、目录结构、monorepo布局、编码规范 |
| **CLAUDE.md（子目录）** | 按需加载，访问该子目录时触发 | 离开子目录后丢失，再次访问才重新加载 | 低 | 特定子目录的规范约定 |
| **Rules** | 会话开始（无范围）或匹配文件时（路径范围） | 压缩时重新注入 | 中 | 跨文件的约束（如所有API必须用Zod验证） |
| **Skills** | 名称和描述会话开始加载，完整内容调用时才加载 | 已调用的skills压缩后重新注入，有共享预算，旧的先被丢弃 | 低 | 程序化工作流（部署、发布检查清单） |
| **Subagents** | 名称/描述/工具列表会话开始加载，body通过Agent工具调用时才加载 | 只有最终摘要返回主会话 | 低（主会话零成本，在自己隔离窗口运行） | 并行任务、深度搜索、日志分析、依赖审计 |
| **Hooks** | 生命周期事件触发 | 完全绕过压缩 | 低（配置在主上下文之外） | 确定性自动化：运行linter、完成后发Slack、拦截命令 |
| **Output Styles** | 会话开始时注入系统提示 | 永不压缩 | 高（但覆盖默认系统提示） | 角色切换（如从编码助手转为通用助手） |
| **Append系统提示** | 会话开始时通过CLI传入 | 仅对该次调用生效 | 中（首次请求后缓存） | 语气、回复长度、格式偏好 |

**几个关键判断：**
- **CLAUDE.md 要控制在200行以内，指定owner**。在 monorepo 中，每个团队的子目录单独维护 CLAUDE.md，用 `claudeMdExcludes` 排除无关团队的配置
- **路径范围的 Rules 优于嵌套的 CLAUDE.md**：当指令涉及跨多个目录的横切关注点时，用 Rules 更合适
- **Subagents vs Skills 的核心区别是隔离性**：Subagents 在自己的隔离上下文运行，不污染主线程，支持5层嵌套，适合并行任务和不需要回看中间结果的任务
- **Hooks 是唯一完全确定性的控制手段**：`PreToolUse` hook 可以拦截任何工具调用，exit code 2 直接拒绝
- **自定义 Output Styles 需谨慎**：默认的编码助手 system prompt 包含范围控制、安全关注、验证习惯等关键指令，自定义覆盖后 Claude Code 会退化为通用助手

这篇文章相当于 Claude Code 的"指令系统架构设计文档"，对于重度使用 Claude Code 的团队有很强的实操参考价值。

## Project Fetch Phase Two — Claude Opus 4.7 自主操控机器人【⭐⭐⭐】

**来源：** Anthropic Research
**链接：** https://www.anthropic.com/research/project-fetch-phase-two
**关键词：** Anthropic、机器人、自主操控、Claude Opus 4.7、Frontier Red Team

### 摘要

Anthropic 前沿红队（Frontier Red Team）发布了 Project Fetch 第二阶段测试结果。核心发现：Claude Opus 4.7 在完全无人类辅助的情况下，自主完成了此前一年前由人类团队完成的所有机器人操作任务，速度比最快的人类团队快约 20 倍。

Project Fetch 的目标是测试 Claude 能否帮助 Anthropic 员工执行复杂的机器人任务。第一阶段让人类操作员通过 Claude 辅助完成，第二阶段则完全移除人类干预——Claude 直接操控机械臂完成一系列精密操作。

这是 AI 从"辅助人类操作机器人"到"自主操控物理设备"的重要里程碑，对 AI 安全、自主系统和机器人产业化都有深远影响。

## Google A2A 协议一周年：多 Agent 协作走向产业落地【⭐⭐⭐】

**来源：** Google AI
**链接：** https://developers.googleblog.com/how-a2a-is-building-a-world-of-collaborative-agents/
**关键词：** Google、A2A协议、多Agent协作、Agent-to-Agent、FoldRun、生命科学

### 摘要

Google 庆祝 Agent-to-Agent（A2A）协议发布一周年，由 Alan Blount、Frank Guan 和 Nick Losier 撰写。A2A 的核心理念是让 AI Agent 之间能够安全、自主地协作和任务交接，无需传统 API 的刚性耦合——每个 Agent 将复杂工作流委托给专业化的对等 Agent，避免上下文污染、确保数据隐私、通过模块化简化应用设计。

文章重点展示了 FoldRun——一个基于 A2A 的生命科学 Agent 界面，用于编排复杂的蛋白质结构预测工作流。此外 A2A 生态已扩展到电商、数据流、DevOps 和电信等多个垂直领域。

这篇博文标志着多 Agent 协作从概念验证进入产业落地阶段。在 Anthropic 大力推进 Claude Code subagents 的同时，Google 选择了开放协议路线，两家公司在 Agent 协作范式的路径分化值得关注。

**关键词：** Claude Enterprise、MCP、OAuth、Okta、身份提供商、集中管理

### 摘要

Claude 企业版新增 MCP 连接器的集中授权管理功能。管理员现在可以通过身份提供商（IdP）为整个组织统一配置和下发 MCP 连接器，首批支持 Okta。用户在首次登录时自动获得连接器访问权限，无需逐个手动配置 OAuth。

## Headroom — LLM 上下文压缩层，省 60-95% Token【⭐⭐⭐】

**来源：** Github Trending Daily
**链接：** https://github.com/chopratejas/headroom
**关键词：** 上下文压缩、Token优化、MCP Server、Kompress-v2、37k Stars

### 摘要

Headroom 是一个 LLM 上下文压缩层，在内容到达 LLM 之前对工具输出、日志、RAG 片段、文件和对话历史进行压缩，号称减少 60-95% token 消耗但保持相同的回答质量。37,075 Stars + 2,524 Forks 反映了市场对"降低 LLM 使用成本"这一痛点的强烈需求。

**三种使用方式：** (1) Python/TypeScript 库直接调用 `compress(messages)`；(2) 代理模式，所有 LLM 请求经过 Headroom 透明压缩；(3) MCP Server，作为 Agent 基础设施集成到 Claude Code、Cursor 等工作流中。

**6 种压缩算法，本地优先，可逆。** 自带 HuggingFace 模型 `Kompress-v2-base`，压缩不依赖云端 API，保证数据隐私。

**与 Anthropic Claude Code 博文的呼应：** 今天 Anthropic 那篇"Steering Claude Code"博文花了大量篇幅讲"上下文成本"——CLAUDE.md 每行都烧 token、Skills 共享压缩预算、Codebase-Memory-MCP 号称减少 99% token 消耗。Headroom 从另一个角度解决了同样的问题：既然上下文很贵，那就压缩它。两者互补：一个好的 Codebase Memory 让 Agent 少读代码，一个好的 Headroom 让 Agent 读到的内容更短。

## Agent-Native — BuilderIO 的 Agent 原生应用框架【⭐⭐】

**来源：** Github Trending Daily
**链接：** https://github.com/BuilderIO/agent-native
**关键词：** Agent框架、A2A协议、BuilderIO、TypeScript、开源

### 摘要

BuilderIO（前端可视化搭建平台 Builder.io 背后的公司）开源了 Agent-Native，一个"Agent 原生应用"框架。核心理念：Agent 和 UI 是同一系统中的平等公民，每个操作都是双向的——可以点击，也可以让 Agent 执行。

**关键特性：**
- **共享状态：** Agent 和 UI 共享同一数据库和状态，任一方变更即时同步
- **实时多人协作：** CRDT 合并，Agent 是一等公民的"协作者"，支持实时游标、选区环
- **上下文感知：** Agent 知道你在看什么，选中文本按 Cmd+I 即可对 Agent 发指令
- **每个用户独立的 Agent 配置：** Skills、Memory、Instructions、Sub-agents、MCP Server 全部 SQL 存储、按用户定制
- **支持 A2A 协议：** Agent 可以调用其他 Agent，跨应用编排任务
- **一次定义、多处使用：** 一个 Action 同时暴露给 UI、Agent、HTTP API、MCP、A2A、CLI

**技术栈：** TypeScript，支持任意 SQL 数据库（Drizzle ORM 适配）和任意部署目标（Nitro）。

BuilderIO 的入局标志着"Agent 应用框架"从概念走向工程化。与 UI-TARS（字节，纯桌面操控）和 Claude Code subagents（Anthropic，纯代码 Agent）不同，Agent-Native 强调的是"人 + Agent + UI"的三方协作——这个定位在 Agent 框架赛道中相当独特。

## LTX-2 — Lightricks 发布第二代音视频生成模型【⭐⭐⭐】

**来源：** Github Trending Daily
**链接：** https://github.com/Lightricks/LTX-2
**关键词：** 视频生成、音频生成、LTX-2、7.4k Stars、开源

### 摘要

Lightricks 发布了 LTX-2，一个支持音频+视频联合生成的模型，并提供官方 Python 推理和 LoRA 训练包。7,442 Stars 热度说明音视频生成是当前 AI 领域最受关注的方向之一。LTX-2 的差异化在于"音视频一体化"——不只是生成画面，同时生成匹配的音频，这在视频生成模型中较为少见。与 Runway、Pika 等闭源商业化产品形成开源替代方案。

## TimesFM — Google 时序基础模型【⭐⭐】

**来源：** Github Trending Daily
**链接：** https://github.com/google-research/timesfm
**关键词：** Google Research、时序预测、基础模型、22.7k Stars

### 摘要

Google Research 的 TimesFM（Time Series Foundation Model）是一个预训练的时序预测基础模型，22,765 Stars。与 LLM 在文本领域的思路类似，TimesFM 试图建立一个"一个模型预测所有时序"的范式。在金融预测、供应链、IoT 等场景有广泛应用前景。这代表了基础模型从语言/视觉向更广泛数据类型的扩展趋势。

## VoxCPM — 清华系开源多语语音生成模型【⭐⭐】

**来源：** Github Trending Daily
**链接：** https://github.com/OpenBMB/VoxCPM
**关键词：** 语音合成、TTS、多语言、声音克隆、30.6k Stars

### 摘要

OpenBMB 发布的 VoxCPM2 是一个无 Tokenizer 的 TTS 模型，支持多语言语音生成、创意声音设计和逼真声音克隆。30,626 Stars 的热度验证了语音 AI 正在成为继文本、图像、视频之后的第四大 AI 模态。无 Tokenizer 的设计意味着更少的信号损失和更自然的语音输出。

## zvec — 阿里开源轻量级向量数据库【⭐⭐】

**来源：** Github Trending Daily
**链接：** https://github.com/alibaba/zvec
**关键词：** 阿里巴巴、向量数据库、嵌入式、C++、11k Stars

### 摘要

阿里巴巴开源了 zvec，一个轻量级、极速的进程内向量数据库（C++编写，11,141 Stars）。与 Pinecone、Weaviate 等独立部署的向量数据库不同，zvec 是嵌入式设计，直接集成到应用中，无需额外服务。特点：轻量、快、零运维。在 RAG 和 Agent 场景中，这种嵌入式向量存储可以大幅降低架构复杂度和延迟。
