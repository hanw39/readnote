## Multigres v0.1 Alpha：Postgres 的操作系统级方案【⭐⭐⭐】
**来源：** Supabase Blog
**链接：** https://supabase.com/blog/multigres-v0-1-alpha
**关键词：** Multigres, Postgres, 水平扩展, 高可用, 连接池, Kubernetes

### 摘要

Supabase 正式开源了 Multigres v0.1 Alpha——一个面向 Postgres 的「可伸缩操作系统」。这个东西的定位是非常明确的：把 Postgres 在生产环境下的运维复杂度（读写分离、故障切换、连接管理、备份）抽象成一个统一的系统层。项目由前 Vitess 核心贡献者 Sugu Sougoumarane 领导，整个架构思路非常「Vitess 味」——先用 Operator + 连接池 + HA 把单集群管好，等 sharding 就绪后直接横向扩展。

v0.1 Alpha 的几个核心组件：

**Kubernetes Operator**：支持在 K8s 上部署 Multigres 集群，可以用本地 Kind 集群测试，备份目标支持共享文件系统或 S3。所有镜像已经公开。

**高可用方案**：这是 Multigres 最体现工程深度的部分。它把 HA 当作一个共识问题来解决，能处理脑裂场景而不丢失已提交的事务。关键亮点：1）直接基于原生 Postgres 复制协议，不需要修改 PG 内核；2）允许用户自定义持久化策略（比如要求跨 AZ 容灾，但不强制 majority quorum），比传统 Raft/Paxos 方案灵活得多；3）可以在集群运行时动态增减副本，不影响性能和一致性。

**连接池**：Multigres 自研了两层连接池架构——multigateway（接受客户端连接并路由） + multipooler（管理后端连接）。几个有意思的设计：1）不需要用户手动选择 pooling mode（transaction/session），因为它内置 SQL 解析器，能理解每条请求的语义，自动判断是否需要保持连接状态；2）按用户维护独立的连接池，用公平分配算法控制连接预算，避免传统 SET ROLE 的安全隐患；3）跨 gateway 去重 prepared statements，同一语句在 PG 内部只解析缓存一次。

**备份**：基于 pgBackRest，从副本上做备份避免拖慢主库。支持全量/增量/差异三种模式，CLI 可以做手动备份和恢复。

当前是 pure open-source release（Apache 2.0），Supabase 的托管版 Multigres 还在后面。Sharding——这个最终的大杀器——也不在 v0.1 里，预计后续版本推出。团队明确说性能 benchmark 还没做完，API 也不稳定，**不建议上生产**。

整体来看，Multigres 试图解决的是 Postgres 生态里最大的一个痛点：当数据量和流量上来之后，运维复杂度指数级增长。目前市面上的方案要么是 Citus（分布式 PG，但运维不简单），要么是托管方案（RDS/Aurora/AlloyDB），要么是自己拼 PgBouncer + Patroni + pgBackRest 一堆组件。Multigres 的野心是把这些都统一起来，还加上未来的 sharding。这次 v0.1 单集群版本相当于先把「地基」亮出来了——HA 和连接池的工程思路确实有深度，值得持续关注。

## Supabase Series F：5亿美元融资，估值100亿【⭐⭐⭐】
**来源：** Supabase Blog
**链接：** https://supabase.com/blog/supabase-series-f
**关键词：** Supabase, Series F, $500M, $10B valuation, GIC, Postgres, Multigres

### 摘要

Supabase 宣布完成 5 亿美元 F 轮融资，投前估值 100 亿美元，由新加坡主权基金 GIC 领投。现有投资方全员参与，Stripe 追加投资，Salesforce Ventures 新加入。

这轮资金有三件事要做：

**加速开源/Postgres 工具开发**：同一天开源了 Multigres v0.1 Alpha（即上篇），定位是 Postgres 的可伸缩操作系统，未来版本将提供 Vitess 级别的水平扩展。配合 OrioleDB（目标今年达到生产就绪），Supabase 的蓝图是打造一个完整的 PG 方案，覆盖 bloat、连接池、Jepsen 级高可用和 sharding。

**支撑高速增长**：过去一年 Supabase 上的数据库启动量增长了 600%，超过 60% 的新数据库由 AI 工具（Claude Code、Codex 等）创建。平台上已有近 1000 万开发者，距离上一轮融资仅 8 个月就翻了一倍。Supabase for Platforms 是增长最快的产品线。

**员工流动性**：团队分布在 50 多个国家，不做 geo-adjusted 薪酬。股票期权有 10 年行权期（离职也不失效），每轮融资允许员工出售最多 25% 的已归属股票。

这轮融资的背景值得关注：Supabase 卡位在「开源 Firebase 替代」和「Postgres 托管」两个赛道的交汇点，而 AI 编程工具的爆发让更多非专业开发者也能建应用、起数据库，直接推高了平台数据库启动量。GIC 领投 + Salesforce Ventures 入场也暗示企业级客户的拓展方向。结合同一天发布的 Multigres 来看，Supabase 正从「开源 Firebase」向「Postgres 全栈平台」转型，融资和产品节奏咬得很紧。

## NVIDIA Nemotron 3 Ultra：550B MoE 推理模型，专为长程 Agent 设计【⭐⭐⭐】
**来源：** Ollama
**链接：** https://ollama.com/blog/nemotron-3-ultra
**关键词：** NVIDIA, Nemotron 3 Ultra, 550B, MoE, 55B active, Agent, Ollama, NVFP4, 1M context

### 摘要

NVIDIA 发布了 Nemotron 3 Ultra，一个 550B 总参数、仅 55B 激活参数的 MoE 开源模型，已经通过 Ollama 云端上线。这模型的定位非常清晰：专为长时间运行的 Agent 工作流设计，能在数百次 tool call 中保持推理质量和一致性。

**核心特性：**

- **Agent 优先设计**：针对 Agent 编排、编程助手（Claude Code）、深度研究和复杂企业工作流优化，可支撑数百步的推理链
- **100 万 token 上下文**：能把整个代码库、长工具调用历史和研究轨迹全部纳入上下文
- **NVFP4 量化**：NVIDIA 自研 4 位浮点格式，减少内存占用同时加速推理，让 550B 模型在单机部署成为可能

**一键集成**：通过 Ollama 可以用一条命令启动，已支持 Claude Code、Hermes Agent、OpenClaw 等主流 Agent 框架。

**性能表现**：在 Agent 生产力、指令遵循和长上下文任务上准确率领先主流开源模型，同时吞吐量最高。据 NVIDIA 的 benchmark（vLLM，10k/2k ISL/OSL），比其它领先开源模型节省最多 30% 成本，处于「高准确率 + 高吞吐量」的最优象限。

值得关注的点：这是 NVIDIA 真正在 Agent 推理场景发力的一次表态。55B 激活参数意味着推理时只加载全量 550B 的十分之一，加上 NVFP4 压缩，经济效益远超同等规模的稠密模型。Ollama 作为首发平台，也说明「开源模型 + 云部署」的发行模式正在成为主流——用户不需要自己搞 GPU，通过 Ollama 的云端 API 就能直接调用。对标来看，这和 Grok、Claude Opus 等商业模型在 Agent 推理场景上直接竞争，但开源的属性让它在定制化和成本上有先天优势。
