## Multigres v0.1 Alpha：Postgres 的操作系统级方案【⭐⭐⭐】
**来源：** Supabase Blog
**链接：** https://supabase.com/blog/multigres-v0-1-alpha
**关键词：** Multigres, Postgres, 水平扩展, 高可用, 连接池, Kubernetes

### 摘要

Supabase 正式开源了 Multigres v0.1 Alpha——一个面向 Postgres 的「可伸缩操作系统」。这个东西的定位是非常明确的：把 Postgres 在生产环境下的运维复杂度（读写分离、故障切换、连接管理、备份）抽象成一个统一的系统层。项目由前 Vitess 核心贡献者 Sugu Sougoumarane 领导，整个架构思路非常「Vitess 味」——先用 Operator + 连接池 + HA 把单集群管好，等 sharding 就绪后直接横向扩展。

v0.1 Alpha 的几个核心组件：

**Kubernetes Operator**：支持在 K8s 上部署 Multigres 集群，可以用本地 Kind 集群测试，备份目标支持共享文件系统或 S3。所有镜像已经公开。

**高可用方案**：这是 Multigres 最体现工程深度的部分。它把 HA 当作一个共识问题来解决，能处理脑裂场景而不丢失已提交的事务。关键亮点：1）直接基于原生 Postgres 复制协议，不需要修改 PG 内核；2）允许用户自定义持久化策略（比如要求跨 AZ 容灾，但不强制 majority quorum），比传统 Raft/Paxos 方案灵活得多；3）可以在集群运行时动态增减副本，不影响性能和一致性。

**连接池**：Multigres 自研了两层连接池架构——multigateway（接受客户端连接并路由） + multipooler（管理后端连接）。几个有意思的设计：1）不需要用户手动选择 pooling mode（transaction/session），因为它内置 SQL 解析器，能理解每条请求的语义，自动判断是否需要保持连接状态；2）按用户维护独立的连接池，用公平分配算法控制连接预算，避免传统 SET ROLE 的安全隐患；3）跨 gateway 去重 prepared statements，同一语句在 PG 内部只解析缓存一次。

**备份**：基于 pgBackRest，从副本上做备份避免拖慢主库。支持全量/增量/差异三种模式，CLI 可以做手动备份和恢复。

当前是 pure open-source release（Apache 2.0），Supabase 的托管版 Multigres 还在后面。Sharding——这个最终的大杀器——也不在 v0.1 里，预计后续版本推出。团队明确说性能 benchmark 还没做完，API 也不稳定，**不建议上生产**。

整体来看，Multigres 试图解决的是 Postgres 生态里最大的一个痛点：当数据量和流量上来之后，运维复杂度指数级增长。目前市面上的方案要么是 Citus（分布式 PG，但运维不简单），要么是托管方案（RDS/Aurora/AlloyDB），要么是自己拼 PgBouncer + Patroni + pgBackRest 一堆组件。Multigres 的野心是把这些都统一起来，还加上未来的 sharding。这次 v0.1 单集群版本相当于先把「地基」亮出来了——HA 和连接池的工程思路确实有深度，值得持续关注。
