## Measuring What Matters with Jules【⭐⭐⭐】
**来源：** Google AI
**链接：** https://developers.googleblog.com/measuring-what-matters-with-jules/
**关键词：** 主动式AI编程助手、Jules、Agent评估基准、SWE-Bench替代方案

### 摘要

Google发布了一篇关于主动式AI编程助手 Jules 的重要研究论文。核心观点：当前AI编程助手正在从"响应式工具"（你问它答）转向"主动引擎"——持续吸收上下文、主动发现风险、在开发者提问之前就给出诊断洞察。

这是一个从"完成任务"到"理解目标"的范式转变。现有基准测试如 SWE-Bench 只能评估 Agent 完成明确定义任务的能力，但对于更高层次的目标（goal），完全没有评估标准。

论文提出了"洞察策略"（insight policy）的概念，即Agent需要能够判断什么值得报告、用什么证据支撑、是打断开发者还是保持沉默。

在评估方法上，团队使用 Google 内部的 705 个真实 Bug（涉及 1178 个代码变更）构建了初步基准：先通过时间邻近性和语义相似性将历史Bug聚类，找到开发者实际在追求的"高层目标"；然后将每个Bug簇中的单个Bug作为"真值"目标，把代码库恢复到修复前的状态让 Agent 去探索；最后用 LLM 对 Agent 的预测洞察进行1-5分评分。

初步结果很鼓舞人心。单轮探索中 Agent 平均得分 4.5/5，说明核心诊断逻辑跑通了。关键发现在于探索轮次的效果：当预算从2轮增加到3轮时，Hit@5准确率从33%飙升至57%，证明多轮探索对复杂问题有实质性帮助。

团队计划将这套评估扩展到公开 GitHub 数据（Issues和解决PR），让整个社区能使用该方法论。目前正在探索如何将 Issue Tracker、设计文档等更丰富的上下文流纳入评估。

横向对比：这是第一个针对"主动式"AI编程助手设计的基准，和传统的 SWE-Bench 形成了互补——后者测试"会不会修"，前者测试"能不能提前发现该修什么"。对于正在构建 Agent 产品的团队来说，这篇论文提供的评估方法值得关注。

**关联论文：** Agentic Coding Needs Proactivity, Not Just Autonomy

## Build Cross-Language Multi-Agent Team with Google's ADK and A2A【⭐⭐】
**来源：** Google AI
**链接：** https://developers.googleblog.com/build-cross-language-multi-agent-team-with-google-agent-development-kit-and-a2a/
**关键词：** 多语言Agent协作、A2A协议、Agent Development Kit、合同合规

### 摘要

一篇非常实战的教程，演示如何用 Google 的 Agent Development Kit（ADK）和 Agent2Agent（A2A）协议构建跨语言多 Agent 团队。场景设定得很有代表性：数据科学团队用 Python + Gemini 做合同条款提取，安全团队用 Go 做合规验证（纯确定性逻辑、不用LLM），两个服务独立运行且都不想重写，现在需要它们协同工作。

文章给出了三个关键架构模式：

1. **A2A协议实现跨语言Agent通信**：通过 Agent Card（类似 OpenAPI 规范）做能力发现，通过 JSON-RPC 2.0 做数据交换，通过 Task 状态机（submitted → working → completed/failed）管理生命周期。Python Agent 和 Go Agent 不需要导入对方的包，只需要说同一个协议。

2. **ADK的 RemoteA2aAgent 抽象**：只需几行代码就能把任何符合A2A规范的远程服务变成本地子Agent。Agent Card 会声明能力、输入输出格式、skills 列表，调用方先 fetch card 就能理解远程Agent能做什么。

3. **Pipeline编排替代单体Prompt**：用 ADK 的 ToolContext.state 在子Agent之间共享状态字典，每步对应一个检查点（INGESTED → EXTRACTED → COMPLIANCE_PENDING → COMPLIANCE_COMPLETE → APPROVED/MANUAL_REVIEW）。每个Agent职责单一、工具精简，避免"一个巨大Prompt配50个工具"的单体式反模式。

文章给出的关键判断：10-15个工具是单Agent的临界点，超过后模型会开始混淆指令、调用错误工具。这个经验数据对于设计Agent系统的架构决策很有参考价值。

完整源码已发布在 GitHub 上。

横向对比：Google的A2A协议 + ADK策略明显在推动"Agent微服务化"——类似10年前后端从单体拆分成微服务的逻辑。Anthropic的Claude Code Plugin生态（见本文其他条目）也在做类似的工作，但走的是更集中的Plugin注册方式。

## The Full Claude Desktop Experience on AWS, Google Cloud, and Microsoft Foundry【⭐⭐⭐】
**来源：** Claude Blog
**链接：** https://claude.com/blog/the-full-claude-desktop-experience-on-aws-google-cloud-and-microsoft-foundry
**关键词：** Claude Desktop企业版、多云部署、SSO、Chat+Cowork+Code统一

### 摘要

Anthropic正式宣布：通过 AWS、Google Cloud 和 Microsoft Foundry 使用 Claude Desktop 的企业用户，现在获得了完整的 Desktop 体验——Chat、Claude Cowork、Claude Code 三合一，不再只有 Cowork 和 Code。

几个关键的企业级能力升级：

- **推理留在企业云内**：推理在客户配置的云区域运行，对话历史本地存储，数据连接器的端点由客户控制，Anthropic收到的遥测数据也可控。
- **全组织SSO部署**：支持 IAM Identity Center、Workforce Identity Federation、Microsoft Entra ID 和任意 OIDC 提供商（如 Okta）。没有共享密钥，终端设备上不存储云凭证。
- **按角色分配权限**：Chat、Claude Cowork、Claude Code 各有独立的 policy key，可以给非技术团队开放 Chat+Cowork，给工程团队开放 Claude Code，逐步扩展。
- **M365连接器**：Claude可以访问邮件和文档，通过企业自己的 Entra 应用，支持租户白名单和GCC High/DoD端点（beta）。最严格场景下可用本地连接器，连接仅停留在设备和Microsoft之间。
- **管理工具链**：通过 Intune、GPO 或 Jamf 推送策略模板，支持离线安装器用于气隙环境，部署前可测试所有连接器。
- **模型安全机制**：model guard 确保路由始终走 Claude，即使在 GovCloud 中配置错误也不会跳转。

引用韩华解决方案（Hanwha Solutions）AI团队负责人 Sarang Oh 的话："我们通过现有云环境快速部署了Claude Desktop，无需单独的供应商合同。一个团队就给全球数百名用户完成了部署，无需重型基础设施。"

横向对比：这是 Anthropic 在企业市场的重要一步——把 Claude 变成了一个完整的、可管控的企业桌面应用，不只是一个 API 或 Web 界面。与 GitHub Copilot 的对比值得观察：Copilot 深度绑定 VS Code 和 GitHub 生态，Claude Desktop 则更强调多云部署、自主管控和独立的桌面体验。

## bytedance/deer-flow【⭐⭐⭐】
**来源：** Github Trending Daily
**链接：** https://github.com/bytedance/deer-flow
**关键词：** 字节跳动、SuperAgent、长周期任务、开源Agent框架、73K stars

### 摘要

字节跳动开源的 long-horizon SuperAgent 框架。核心能力描述：借助沙箱、记忆、工具、技能、子Agent和消息网关，处理从几分钟到几小时的不同级别任务。当前 73,770 stars。

这是一个"研究+编码+创作"三位一体的超长周期 Agent 框架，显然瞄准了当前 Agent 领域最大的痛点之一——长任务的可靠执行。字节在大模型领域的布局（豆包等）加上这个框架，展示了一条从模型到 Agent 应用的完整路径。

横向对比：与 Google 的 ADK+A2A（跨语言微服务式Agent）和 Anthropic 的 Claude Code Plugin（集中式插件生态）不同，deer-flow 更像是一个"全能型 Agent 操作系统"，集成了沙箱、记忆、子Agent编排等全栈能力。三种路线代表了当前 Agent 架构的三个方向：协议互联 vs. 插件注册 vs. 全栈操作系统。
