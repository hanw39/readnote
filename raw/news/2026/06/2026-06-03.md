## Claude Code 动态工作流：为每个任务定制编排引擎【⭐⭐⭐】

**来源：** Claude Blog
**链接：** https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code
**关键词：** Dynamic Workflows、Multi-agent、子代理编排、并行执行、对抗验证、Claude Code

### 摘要

Anthropic 上周在 Claude Code 中发布了 **Dynamic Workflows（动态工作流）**——Claude 现在可以在运行时编写自己的 JavaScript 编排脚本（harness），按任务需求动态协调多个子代理。这篇文章由 Anthropic 团队成员 Thariq Shihipar 和 Sid Bidasaria 撰写，详细介绍了工作流的动机、模式和最佳实践。

**为什么需要动态工作流：**
默认的 Claude Code 在单一上下文窗口中既规划又执行。这对多数编码任务有效，但在长时运行、大规模并行、高度结构化或对抗性任务中会暴露三个失败模式：

1. **代理懒惰（Agentic laziness）**：Claude 在复杂多步骤任务中提前停止，比如安全审计做了 35/50 项就宣称完成
2. **自我偏好偏差（Self-preferential bias）**：倾向于偏好自己的结果，尤其在自我验证时
3. **目标漂移（Goal drift）**：多轮对话和上下文压缩后，边缘需求或"不要做X"等约束逐渐丢失

工作流通过为每个子代理分配独立上下文窗口和聚焦目标来对抗这些问题。

**动态 vs 静态工作流：**
之前的 Agent SDK 和 claude -p 可以创建静态工作流，但静态流程要覆盖所有边界情况，通常比较泛化。Opus 4.8 加上动态工作流后，Claude 能针对你的具体场景量身定制编排脚本。

**六种核心模式：**

1. **分类派发（Classify-and-act）**：分类代理判断任务类型 → 路由到不同的处理代理
2. **扇出合成（Fan-out-and-synthesize）**：大任务拆成小步骤 → 并行执行 → 汇总合成。合成步骤是屏障点，等待所有扇出代理完成后合并结构化输出
3. **对抗验证（Adversarial verification）**：为每个执行代理配备独立的验证代理，按评分标准对抗性审查输出
4. **生成过滤（Generate-and-filter）**：批量生成方案 → 按评价标准过滤 → 去重 → 只返回最高质量的结果
5. **锦标赛（Tournament）**：N 个代理用不同方案竞争同一任务 → 评判代理两两对比 → 选出优胜者。文章指出对比判断比绝对打分更可靠
6. **循环至完成（Loop until done）**：工作总量不确定时，循环生成代理直到停止条件满足

**实际应用场景：**

- **迁移和重构**：Bun 从 Zig 重写到 Rust 就用了工作流。秘诀：把任务拆成步骤（调用点、失败测试、模块等），每个修复派一个子代理在独立 worktree 中执行，再由对抗代理审查后合并
- **深度研究**：Claude Code 内置的 /deep-research 技能就是工作流驱动的——扇出网页搜索 → 获取源 → 对抗性验证声明 → 合成引证报告。也可以对 Slack 上下文、代码库探索等做类似研究
- **深度验证**：识别所有事实主张 → 每个主张派子代理验证 → 验证代理再检查源质量
- **排序**：对 1000+ 行项目做定性排序时，单一 prompt 质量会下降。改用锦标赛（两两对比代理）或分桶并行排序
- **规则遵守**：把 CLAUDE.md 中常被忽略的规则拆成独立验证代理（每条规则一个），并让一个怀疑者代理审查规则本身以避免误报
- **排查根因**：从日志、文件、数据中分别提取证据生成独立假设 → 每个假设面对一组验证和反驳代理。不限于代码，也适用于销售下滑分析、数据管道故障等
- **大规模分流**：分类代理对 backlog 分类 → 去重 → 可以尝试修复或升级给人。关键模式是"隔离（quarantine）"——读取不可信公共内容的代理不能执行高权限操作。配合 /loop 实现持续分流
- **探索和品味判断**：UI 设计、命名等需要品味的问题，让审查代理按评分标准筛选方案，打分满意才停止
- **轻量评估**：在独立 worktree 中生成输出 → 对比代理按标准比较并打分
- **模型和智能路由**：分类代理先调研任务复杂度，再决定用 Sonnet 还是 Opus

**什么时候不用工作流：**
文章明确警告——工作流消耗更多 token，不是每个任务都需要。日常编码任务不需要 5 个 reviewer 的面板。判断标准是"它真的需要更多算力吗？"

**实用技巧：**
- 详细提示 + 具体模式描述效果最好
- 可以用"quick workflow"做轻量对抗审查
- 搭配 /goal 和 /loop 实现定时重复执行
- Token 用量可以设预算上限（"use 10k tokens"）
- 工作流可以保存到 ~/.claude/workflows 或打包进 skill 分发给团队。打包时建议提示 Claude 把工作流当模板而非逐字脚本

## 运行AI原生工程团队【⭐⭐】

**来源：** Claude Blog
**链接：** https://claude.com/blog/running-an-ai-native-engineering-org
**关键词：** AI原生团队、agentic coding、工程管理、代码审查、团队组织变革

### 摘要

Anthropic 工程总监 Fiona Fung（Claude Code 和 Claude Cowork 团队）在 Code w/ Claude SF 2026 上分享了 agentic coding 成为默认工作方式后，工程团队的流程和组织发生了怎样根本性的变化。

**核心变化：**

1. **瓶颈转移**：写代码、写测试、重构不再是瓶颈——验证、代码审查和安全成了新的瓶颈。"我们都能快速生成大量代码了，但问题变成了：这代码对吗？怎么维护？人类怎么跟得上代码审查？"

2. **从长期规划到 JIT 规划**：团队放弃了六个月路线图（第三条月就过时了），转向"即时规划"（JIT planning）。不再写设计文档，改为在 PR 和原型中讨论。流程变成"做原型→让内部用户用→根据反馈迭代"。

3. **"谁改的这段代码"不再有效**：所有 PR 都有 Claude 参与，所以这个问题没意义了。新范式是退回到本质——你到底需要知道什么？直接问 Claude，让 Claude 带着数据和上下文回答。

4. **自动化一切**：每天早上手动汇总客户反馈的仪式变成了自动运行的后台任务。团队原则是：任何重复性问题都问"能不能自动化？"

5. **代码审查的分工**：Claude 处理风格检查、linting、PR 反馈请求、bug 修复、测试补充。人类聚焦在真正需要专业判断的地方：法律审查、安全敏感代码、产品品味和审美。

6. **角色重塑**：PM 开始大量写代码，非传统程序员能做更多工程工作，工程师跨界做内容和设计。

7. **招人标准变了**：Fung 强调两个画像——有产品嗅觉的创造性 builder 和有深厚系统专长的工程师。**原始产出量不重要**，模型已经解决了这个问题。关键是"人类专长真正需要的地方"。

8. **团队自治**：几条不可协商的核心原则外，每个 pod 自主决定如何使用 Claude 做 triage、规划仪式和哪些流程优先"Claudify"。

9. **三个指标**：Fung 建议每个工程 leader 跟踪三个数字，同时警告不要混淆吞吐量和成功——真正的指标是你想解决的问题。

**最有价值的建议**：找到团队里最吵闹的流程（最贵的、最让人恐惧的），问两个问题：它还在发挥作用吗？能自动化吗？Fung 举例说她曾经在一个团队里问了句"我们为什么每周花这么多人开这个会？"——于是会议被取消了。
